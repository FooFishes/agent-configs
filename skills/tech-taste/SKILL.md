# tech-taste：个人技术品味

这个 skill 维护的是品味，不是规范。规范是团队层面的、可以查文档的东西；品味是一个人做技术决策时的倾向、审美和底线，只能从一次次对话里慢慢提炼出来。有了这份品味，不管是 Claude Code、Codex 还是 Pi，都能像一个共事多年的同事那样知道用户会怎么选，不用每次从头解释。

品味也不是履历。这里写的应该是偏好，读完让人知道用户下次会怎么选，而不是知道用户过去做过什么。一个项目里的具体选型、一次顺口的指令，都不是品味，只有换一个项目、换一种语言仍然成立的东西才是。

## 文件怎么放

```
tech-taste/
├── SKILL.md          入口，只讲怎么记、怎么用
└── ref/
    ├── CATALOG.md    目录，所有文章按分组列在这里，永远先读它
    ├── _template.md  新建文章时复制这个
    └── <article>.md  一个主题一篇文章，文件名尽量短，比如 errors.md、deps.md
```

SKILL.md 本身不存任何品味，品味全部在 ref 目录里。CATALOG.md 是唯一的入口，先读目录，再按需要打开具体的文章。这样文章再多，每次进上下文的也只是一张目录。

## 什么时候用，怎么用

### 开始干活之前，先查品味

凡是有技术决策空间的工作，写新代码、改架构、选库、重构、做 review、写方案，开始之前先读一遍 CATALOG.md，挑出和手头任务相关的一到三篇文章读一下，把里面的立场带进后面的工作。不用全读，目录就是用来挑的。

如果品味和业界的常规做法冲突了，按品味来。唯一的例外是品味会带来明显的正确性或安全问题。遇到这种冲突的时候照品味做，然后在回复里点一句"这里按你的品味选了 X，没用常规的 Y"，让用户知道这是有意的，不是没想到。

做 review 的时候这一步尤其重要。先把相关文章里的立场列出来，再逐条对照代码，指出哪里和品味不一致，并且引用对应的条目。

如果任务涉及的领域在目录里完全没有记录，那就正常做。做完之后如果用户对结果表达了明确的倾向，这就是一次记录的机会。

### 对话中听到品味，随手记下来

什么算品味信号。最强的信号是纠正，比如"不要用 X"、"别这样写"、"这里应该……"，因为纠正说明默认做法不合口味。其次是明确的表态，"我喜欢……"、"我讨厌……"、"我一直都……"、"以后都这样"。再就是带理由的拍板，用户在几个方案之间选了一个并且说了为什么，这时候理由比选择本身更值得记，因为理由能泛化到下一次。最后，同类建议被否了两次以上，即便用户没有明说，也可以当作一个信号。

什么不算。只对当前项目成立的约束不算，比如"这个 repo 必须用 Node 18"，那是项目 CLAUDE.md 的事。某个项目里的具体选型也不算，比如这个项目用了哪个状态管理库、哪套部署流水线、哪个开源协议，除非同样的选择在两个以上项目里重复出现，或者用户说了一个能迁移到别处的理由。团队或公司的规定不算，那不是个人品味。用户对 Agent 工作方式的偏好也不算，比如回复风格、什么时候该问、要不要用 worktree，这些已经在 ~/.claude/CLAUDE.md 和 memory 里了，不要在这里重复。一次性的指令和情境判断也不算，"给超链接加下划线"、"这个 PR 先不加测试"都只是一次指令，要等它重复出现，或者用户明说这是通用原则。

拿不准的时候问自己一句：换一个项目、换一种语言，这条还成立吗？成立就是品味，不成立就不是。再问一句：这条是在说用户会怎么选，还是在说用户做过什么？后者是日志，不要记。

### 直接写，还是先问一句

用户明确要求记录的，直接写。用户做了明确的纠正或表态的，也直接写，然后在回复末尾用一行告知写了什么、写到了哪篇，用户随时可以让你删或改。只有隐含的倾向，比如一次拒绝、一个没说理由的选择，不要直接写，先问一句"这条要记进技术品味吗"，用户点头再写。

这么分的原因是，明确的纠正已经够清楚了，再问一遍是打扰；而隐含的倾向有误判的风险，问一句的成本比写错一条再清理要低得多。

### 记录的步骤

先读 CATALOG.md，判断这条属于哪篇已有的文章，还是需要新开一篇。

打开目标文章，看看有没有相同或相近的条目。已经有了而且一致，就不重复加，必要时补充一下例子或理由。已经有了但是冲突，以这次的新表态为准，改写旧条目，并在文章末尾的"演变"里记一笔旧立场和改变的时间。品味是会变的，变化本身也值得记录。没有的话，按文章里的条目格式新增一条。

如果要新开文章，复制 _template.md，文件名用一个简短的英文词，然后把开头那句"一句话立场"先写出来。

最后更新 CATALOG.md。新文章放进合适的分组，一行写上描述和一句话立场；已有文章的立场变了就改那一行。然后在回复里用一行告知结果。

### 条目怎么写

每一条品味回答三个问题：结论是什么，为什么，什么时候不适用。具体格式在 _template.md 里。

结论要写成一句能直接执行的判断，比如"错误在边界处统一转换，内部直接抛"，而不是"关于错误处理的一些想法"。理由先用自己的话把道理说清楚，让一个没见过这些项目的人也能理解并泛化到下一次，然后最多引一两句最能体现语气的原话作证据。原话是证据不是正文，把原话堆成一段就成了会议纪要。例外要诚实，没有就写"暂无"，不要为了显得全面而编。来源写出现过的项目名和大致年月就够，不用精确到哪一天哪句话。

条目宁少勿碎。几条说的是同一个倾向就合成一条，一篇文章十条左右为宜，超过了先想能不能合并，确实是两个领域才拆。

## 文章怎么命名、怎么分组

文件名要短，最好一个词，小写英文。文章具体覆盖什么写在 CATALOG.md 的描述里，不要把含义塞进文件名，用 errors.md 而不是 error-handling-and-logging.md。文件名是给人在目录里扫一眼用的，描述才是解释。

分组只存在于 CATALOG.md 里，文件本身全部平铺在 ref 目录下，不建子目录。下面这些主题可以参考，不用预先建好，用到再建。

- 设计：`arch` 讲分层、模块边界、抽象时机、单体与拆分；`api` 讲接口形状、命名、版本、错误返回；`data` 讲数据结构、schema、数据库选型。
- 代码：`naming` 讲命名偏好；`style` 讲函数长度、注释密度、重复与抽象的取舍；`types` 讲类型系统用到什么强度、对 any 和 unknown 的态度；`errors` 讲异常与返回值、边界处理、日志。
- 质量：`testing` 讲测什么、不测什么、测试的粒度；`perf` 讲何时优化、可读性与性能的取舍；`docs` 讲文档和注释写给谁、写多少。
- 工具链：`deps` 讲选库的标准、什么时候自己写、对框架的态度；`tooling` 讲构建、lint、格式化、包管理；`git` 讲提交粒度、分支、commit message。
- 语言：某种语言特有的品味，文件名直接用语言名，比如 `go`、`ts`。

一篇文章超过十条就先想合并，合并不了、确实是几个子领域才拆。文章数量也一样，能并进已有文章的就不新开。

## 平时怎么维护

不需要定期整理，每次写入的时候顺手做几件事就够了。发现两条说的是一回事，合并。发现某一条和用户现在的做法不符，问一下是品味变了还是当时记错了，然后改。发现一篇文章的"一句话立场"已经概括不了里面的条目，重写那句话。目录里每一行的描述和立场，应该让人不打开文章就大概知道里面是什么。

## 手动命令

`/tech-taste` 后面可以跟这几种参数。不带参数或者 `show`，读目录，概述目前有哪些主题、各自的核心立场。`record <内容>`，把这段话按上面的步骤记录进去。`review`，按品味审查当前改动或指定文件。直接跟一个主题名，展示那一篇文章的内容。
