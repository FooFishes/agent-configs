# docs

一句话立场：注释只写 What 和 Why，半角标点，不口语不长文。文档是事实源，只保留对照过源码的现行文档。行文要流畅自然，用列表不用表格。

## 条目

### 注释只写 What 和 Why，半角标点，文档注释形式，不口语不长文，有缺陷的代码必须写 TODO

为什么：口语不只是用词，"很多表述完全是按照口语的习惯去写的, 读起来很难受"。写说明文，不写旁白。长的要拆。配置文件里不留解释性注释。

例外：暂无。

来源：Nova、eat_what_app，2026-10 至 11。

### 文档是事实源：选型、协议、功能增删都写回文档，删功能时文档一起改

为什么：文档和代码不同步，文档就成了误导。"写回文档"在一个项目里说了至少六次。

例外：暂无。

来源：Nova、eat_what_app，2026-10。

### 只保留现行核心文档，内容对照源码核实；只写已实现、能被代码证实的能力

为什么：一次性的修复报告不积累，docs 从一百三十个文件收敛到核心几份。讲稿和文档里"草稿里提到的点要逐一和代码核对"。

例外：暂无。

来源：training-sys、AnkerHackathon，2026-09 至 10。

### 产品文档描述最终形态，是开发的指导不是实现的说明；规范类文档写原则和为什么，不用代码细节指点实现

为什么："产品文档并非技术实现的说明, 而是技术开发的指导"，不和后端当前实现耦合。规范文档可以详细严肃，但"用代码去指点"就过了。

例外：暂无。

来源：eat_what_app，2026-10。

### 提炼通用经验必须剥离项目细节，夹着项目 spec 的不算通用

为什么：总结经验时看到结果说"感觉并不通用, 里面还有很多项目 spec"。本品味库第一版也因为同样的问题重写过。

例外：暂无。

来源：AnkerHackathon、agent-configs，2026-10 至 11。

### Markdown 用列表不用表格，内容分组；入口文件只做目录，正文放子文章；行文要流畅

为什么：表格在终端和 diff 里都难读，分组比平铺好找。"我不太喜欢你在这个 SKILL 中的遣词造句行文, 感觉不是很流畅诶"。

例外：暂无。

来源：agent-configs，2026-11。

### 每个项目一套固定文档：产品、选型、架构、计划，加 OpenAPI、简练的 README 和详细的 AGENTS.md

为什么：两个项目用了同一套清单，没有的先建占位文件。README 给人看要短，AGENTS.md 给 Agent 看要全。

例外：暂无。

来源：isdu-app、eat_what_app，2026-09 至 10。
