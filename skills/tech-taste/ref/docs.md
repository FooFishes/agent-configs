# docs

一句话立场：注释只写 What 和 Why，半角标点，不口语不长文；文档是事实源，决策写回文档，只保留对照过源码的现行文档；行文要流畅自然。

## 条目

### 注释只写 What 和 Why，半角标点，写成文档注释；有缺陷的代码必须写 TODO

为什么：用户先要求"对目前的所有注释, 进行审查. 请你说一下你认为注释应当怎么写"，然后纠正："必须使用半角符号. 此外, 尚有缺陷的代码必须写 TODO. 目前还有超级多的口语, 并不是你认为的那样比如口语用词才是口语, 很多表述完全是按照口语的习惯去写的, 读起来很难受. 并且不宜写长文, 要适当的拆分."这些后来沉淀成 COMMENT-STYLE.md，派任务时主动引用"注释遵守 docs/guideline/COMMENT-STYLE.md (只写 What 与 Why, 半角标点, /** */)"，还把"中文UI和注释的合成一个 Skill"。

例外：暂无。

来源：2026-10-13 Nova；2026-10-26 scratch；2026-11-01、11-02 eat_what_app。

### 不口语化：口语不只是用词，更是按说话习惯组织的句子

为什么：同上。"很多表述完全是按照口语的习惯去写的, 读起来很难受"。写说明文，不写旁白。

例外：暂无。

来源：2026-11-01 eat_what_app。

### 文档是事实源：选型、协议、功能增删都写回文档，删功能时文档一起改

为什么：Nova 里至少六次："会开源，用 AGPL 吧，写回文档"，"OK 写回去吧"，"直接去掉整理功能, 文档一起改。"，"并更新选型与架构文档"。eat_what_app："先提交产品文档，再对照产品文档查看其他文档是否存在问题，一切以产品文档和最新的三个文档为基准。"

例外：暂无。

来源：2026-10-12 至 10-21 Nova；2026-10-22 eat_what_app。

为什么："你看看 docs/ 下还有有用的文档吗"，"把没用的移除一下吧. 只保留核心文档, 并且里面内容也要确认是否为最新"。docs 从一百三十个文件收敛。

为什么："将 产品文档(如有) 放到 docs/EatWhat_产品文档.md ... 依赖选型 ... 技术架构 ... 开发计划 ... 对于没有的文档, 创建占位 .md 文件 ... 创建一个简练的 README.md ... 为该项目创建详细的 AGENTS.md 并链接 CLAUDE.md"。isdu-app 也维护着一份文档清单。

### 产品文档是开发的指导不是实现的说明，描述最终形态，不和后端实现强耦合

为什么："这份产品文档是描述这个产品的最终形态. 可以不关心后端目前的实际实现... 需后端和待接入都不是产品文档该做的, 这个反而应当单开文档. 产品文档要做的, 是确认各个功能的实现细节. 你目前做的还不错, 但是和后端实现太强耦合了, 产品文档并非技术实现的说明, 而是技术开发的指导"。

例外：暂无。

来源：2026-10-21 eat_what_app。

### 梳理类文档按功能分类、功能点、实现细节三层写，关键处放少量伪代码和接口名；给人的出 HTML，给 AI 的出 Markdown

### 开发计划按里程碑粗粒度拆，不拆太碎；先头脑风暴确认设计再写文档或代码

为什么："规划一下项目开发计划, 不要拆的太碎, 我们需要进行 Vibe Coding"；"先别写文档, 和我头脑风暴设计一下先"；"在开始写之前, 先确认产品形态与功能. 然后, 给我几个设计风格(with components)供我候选, 4-6个."

例外：偏工作流程，但体现"设计先于实现"的习惯。
