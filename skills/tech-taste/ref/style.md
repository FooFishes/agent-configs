# style

一句话立场：写简练，用成熟库不手写轮子，优先最简单的做法；代码陈旧宁可彻底重做，不留兼容层和死代码。

## 条目

### 写简练，不要写复杂

为什么：同一句话说了两次："写的太复杂了, 写的简练一些"。

例外：暂无。

来源：2026-10-13 Nova。

### 优先用成熟的框架和依赖，手写本可以用库解决的东西算坏味道

为什么：审查时主动把这当作一类问题来找："是否有地方使用了手写而非使用成熟的框架或依赖. 是否有地方写了不符合最佳实践的代码, 是否有地方有更好的实现方案."。前端"对于组件可以使用成熟的UI库, 但是一定要符合原始的视觉风格"。Codex 那边据此把手写的用户缓存、订阅、轮询换成了 TanStack Query，用户逐个提交接受。

例外：决策核心和业务逻辑例外，见 llm 和 arch。

来源：2026-09-04 sentry-panel-frontend；2026-09-27 training-sys。

### 优先选最简单的做法，能用库的一个配置项解决就不写逻辑

为什么："优先选简单做法: 给 anonymous() 传 disableDeleteAnonymousUser: true. 如果更合理, 也可以用 onLinkAccount"。

例外：暂无。

来源：2026-10-15 AnkerHackathon（会话简报转述）。

### 没有外部消费者就不留兼容层、不做过渡期、不保留死代码

为什么：这是跨项目最一致的态度之一。"全部迁移, 不进行旧代码的兼容或过渡."，"因为当前的代码比较陈旧, 所以我们会做比较彻底的修改, 可以不考虑存量代码的兼容或者过渡."，审查时同一个问题发了三次："有没有哪里是写了过多的无用兼容代码(背景: 我们这是内部自用平台, 无存量代码与存量数据, 一切以当前版本为最新版. 只有内部这一个前后端组合, 无其他第三方使用)"。旧认证路径"进行剥离"，一次性代码"删掉就好"，没用的接口要主动找出来。判断标准是"有没有真实的第三方消费者和存量数据"。

例外：有外部消费者或存量数据时另议，但先问清楚有没有，不要假设有。

来源：2026-09-26、09-27 training-sys；2026-09-07 sentry-panel。

### 代码质量差时推倒重做，直接给最终形态，不做过渡性的 MVP

为什么："请你移除这个项目目前所有实现的代码,我们推倒进行重头开发"，"直接给出最终的产品形态, 不需要中间测试的 MVP 应用"。三个项目、两种语言都这么做过。

例外：暂无。

来源：2026-09-03 SentryPanelBackend；2026-09-04 sentry-panel-frontend；2026-09-27 training-sys。

### 配置文件里不留注释

为什么："移除 ci.yml 的注释"。和注释规范一致：不写解释性噪音。

例外：暂无。

来源：2026-10-12 Nova。

### 字段和类型的命名细节交给实现者按惯例定，用户只锁结构

为什么："上述字段名仅作为参考, 具体所有的命名按照你的看法进行编写"。不在命名上纠结，关注的是模式和形状。

例外：暂无。

来源：2026-09-27 training-sys。

### 文件名和标识符保持简短，含义交给描述

为什么："不要把文件名写的很冗长"，"名字就用 zh-dev-writing"。

例外：暂无。

来源：2026-10-26 scratch；2026-11-07 agent-configs。

### 同一类问题在所有代码路径上的处理要一致

为什么：ZIP 中文文件名编码有两处回退逻辑，用户拍板"改吧，两边统一用 GB18030 回退"。

例外：暂无。

来源：2026-10-06 training-sys。

### 层级信息用目录结构表达，不把多个维度拼进文件名

为什么："课程名_作业标题_学号_姓名_v3_原文件名 这种应当是按照文件夹分层,而不是按照文件名去区分"，批量下载"不进行压缩包嵌套, 而是在压缩包内进行文件夹层级的嵌套"。文件名要有稳定、有辨识度的信息，但"已选12份 这种信息就不需要了"。

例外：暂无。

来源：2026-09-29 training-sys。

### 严格按视觉原型实现，项目结构按框架的最佳实践组织，两者不混

为什么："请你严格按照我们给的prototype, 进行开发吧. 但是项目结构还是采用React的最佳实践."

例外：暂无。

来源：2026-09-04 sentry-panel-frontend。

### 质疑没有实际价值的包装层和防御性检查，说不清为什么存在的就删

为什么：Review 别人的提交时第一反应是"AppSafeArea 有意义吗"；看到多余的检查说"这个检测并无意义, 去掉这种写法"；对看起来奇怪的写法要求给理由："现在的 Endpoints 写法很怪, 这么写对的原因是什么"。没用的功能、莫名其妙的测试、键盘操作，都是"去掉"。

例外：暂无。

来源：2026-10-19 isdu-app；2026-11-04 eat_what_app。

### 删掉东西时补一句说明，不静默删除

为什么："删掉吧, 然后补一句说明"。

例外：暂无。

来源：2026-11-04 eat_what_app。

### 重写逻辑层时允许自由引入依赖，不限制数量，看重的是用成熟库把事做对

为什么："UI 尽可能保证完全的不改变, 同时逻辑层完全的重写, 使用最佳实践, 可以引入所需的依赖, 并且并不限制依赖的引入量"。对"少依赖"没有执念。

例外：暂无。

来源：2026-10-08 isdu-app。
