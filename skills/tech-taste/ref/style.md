# style

一句话立场：代码要简练，能删的都删。没有真实消费者就不留兼容层和死代码，陈旧的代码宁可推倒重做，能用成熟库就不手写。

## 条目

### 写简练，优先最简单的做法

为什么：复杂是默认倾向，不加约束的话逻辑会自己长出来。评价一段代码的第一标准是简练，能用库的一个配置项解决的事就不写一段逻辑。原话是"写的太复杂了, 写的简练一些"。

例外：暂无。

来源：Nova、AnkerHackathon、eat_what_app，2026-10 至 11。

### 没有真实的外部消费者和存量数据，就不写兼容层、过渡期、fallback 和正常走不到的错误分支

为什么：兼容代码唯一的正当理由是有人依赖旧行为。自己掌控前后端、没有存量数据的时候，兼容层只是噪音，还会掩盖真正的契约变化。审查时会专门把"过多的无用兼容代码"当一类问题来找，前提也是自己说清楚的：内部自用，无存量，一切以当前版本为最新。开发期的客户端同样严格按后端最新实现，不为联调写兼容分支。

例外：有外部消费者或存量数据时另议，但先问清楚有没有，不要默认有。

来源：training-sys、sentry-panel、eat_what_app，2026-09 至 11。

### 代码质量差或已陈旧时推倒重做，直接给最终形态，不做渐进迁移，也不做过渡性 MVP

为什么：新老机制混跑会让修 bug 期间两套逻辑并存，渐进迁移的中间态本身就是成本。三个项目、两种语言都选了整体重写，旧代码放到 legacy 分支留档就够了。

例外：暂无。

来源：SentryPanel 两端、training-sys、isdu-app、eat_what_app，2026-09 至 10。

### 说不清为什么存在的包装层、防御性检查、功能、文案和测试直接删，删的时候补一句说明

为什么：每一层包装和每一个检查都要能回答"它防的是什么"，回答不出来就是噪音。Review 时第一反应常常是"这有意义吗"，看到奇怪的写法会要求给出"这么写对的原因"。

例外：暂无。

来源：isdu-app、eat_what_app，2026-10 至 11。

### 成熟库优先，手写本可以用库解决的东西算坏味道，不限制依赖数量

为什么：手写的缓存、轮询、状态同步几乎总是比成熟库的实现更脆弱。审查时会主动找"手写而非使用成熟框架"的地方，重写逻辑层时明确"不限制依赖的引入量"。对"少依赖"没有执念，看重的是把事做对。选库时看当前使用率和维护活跃度。

例外：产品的决策核心和业务逻辑自己写，见 llm。

来源：sentry-panel、training-sys、isdu-app、eat_what_app，2026-09 至 11。

### 同一类问题在所有代码路径上的处理方式要一致

为什么：两处回退逻辑不一样，就等于埋了一个只在特定路径触发的 bug。发现不一致时拍板"两边统一"。

例外：暂无。

来源：training-sys，2026-10。

### 文件名和标识符保持简短，含义交给描述；层级信息用目录结构表达，不拼进文件名

为什么：名字是给人扫一眼用的，解释是描述和文档的事。把多个维度拼进文件名，等于把目录树压扁成一个字符串。

例外：暂无。

来源：training-sys、agent-configs，2026-09 至 11。

### 有预设就用预设，偏差不大的向预设靠拢，但不禁止零散写

为什么：这是对"全部令牌化"的回拨。规范是为了一致，不是为了把每个数字都抽成变量。

例外：暂无。

来源：eat_what_app，2026-11。
