# api

一句话立场：响应和错误走同一个结构化出口，带业务码、HTTP 状态和用户看得懂的消息。契约进仓库，未定的留空不编。错误修根因，缺失的数据按缺失处理。

## 条目

### 响应统一包成泛型的 code、message、data，成功码 0，业务码全局单一编号空间

为什么：前端判成功只看一个字段。不按模块拆码是因为"没有拆分模块"，不为不存在的边界预留结构。

例外：暂无。

来源：training-sys，2026-09。

### 错误结构化：定义带 HTTP 状态、业务码和消息的错误枚举，业务点抛业务异常，全局处理器统一转成同一响应结构

为什么：理由是自己写出来的：裸异常走统一处理时"业务信息并不好进行传递, Http Status Code 不好判断"。错误和成功响应结构一致，前端才能用一套逻辑。框架层和过滤器层抛出的错误也要兜住，走同一格式。Spring 里叫 BizCode 和 BizException，别的语言形态不同，模式一样。

例外：暂无。

来源：training-sys，2026-09。

### 服务端的原始消息带到前端但不直接展示，用户看到的是友好文案；返回值不能被静默忽略

为什么：原始错误是给开发者的，用户看到的应该是能做什么。信息要完整带到前端，否则排查时没线索。

例外：封禁原因、操作受限原因这类本来就写给用户的内容可以直接展示。

来源：training-sys、eat_what_app，2026-09 至 10。

### 缺失的数据按缺失处理，显式说明是未接入、不可用还是范围不匹配，不用 0、空数组或占位数字伪装

为什么：出自自己写的产品审阅文档。假数据比没数据更糟，它让人以为系统正常。缺分母时比例是 null，不是 0。

例外：暂无。

来源：sentry-panel，2026-09 至 10。

### 遇到超时、卡住、报错先查根因，不接受加 limit、加 timeout 或放宽断言止血

为什么："为什么 60s 都没有响应呢 不应该只加 limit"。止血会把真正的问题藏到更深处。

例外：暂无。

来源：AnkerHackathon，2026-10。

### OpenAPI 进仓库作为前后端契约，用脚本同步，定期对照代码找偏差；未定的部分留空不编

为什么：编出来的字段比缺字段更难发现。"格式不知道, 你不会不写吗"，"哪里说是 null, 找一下依据"。与后端的差距列成 checklist 逐条拍板，不自行猜。

例外：暂无。

来源：isdu-app、eat_what_app，2026-09 至 11。

### 端点、枚举这类常量集中声明并保持完整，不散落字符串字面量，不接受半截枚举

为什么：散落的字面量改一处漏一处，半截枚举等于未定义行为。

例外：暂无。

来源：isdu-app、eat_what_app，2026-10 至 11。

### schema 变更和新增迁移先问；全新部署、无存量的项目不考虑旧数据

为什么：迁移不可逆，要知情。没有存量数据时为旧数据写兼容也是在给不存在的消费者写代码。

例外：暂无。

来源：training-sys，2026-09 至 10。
