# errors

一句话立场：错误要结构化地带着业务码、HTTP 状态和用户能看懂的消息走统一出口；修错误修根因，不加超时或放宽断言糊过去。

## 条目

### 不抛裸的运行时异常，定义带 HTTP 状态、业务码和消息的错误枚举，抛业务异常，全局处理器统一转成响应

为什么：用户自己把模式写得很完整："现在后端对于错误的处理方式是抛出 RuntimeException 然后走统一的错误处理. 但是这样存在问题: 业务信息并不好进行传递. Http Status Code 不好判断. 现在需要改成这种模式: 1. 定义 BizCode(HttpStatus, code, msg) 2. 定义 BizException(BizCode) 3. 错误点throw BizException(BizCode) 4. 全局 Handler 从 BizException 中提取 BizCode, 放入 ResultEntity 进行返回. 以便于在错误场景下也遵循 {code, message, data} 的响应"。理由是两点：业务信息要能传递，HTTP 状态码要能判断。

例外：暂无。

来源：2026-09-27 training-sys。

### 全局错误处理要兜住框架层和过滤器层的错误，面向用户的消息要友好

为什么："记得完善一下 全局 Handler, 提示消息要 User Friendly"，"Security 的不合理也进行修改. 保证我们的走向是统一的或者是明确的"。Spring Security 过滤器链里抛出的错误也要走同一种响应格式。

### 不把服务端的原始错误消息和错误码直接展示给用户

为什么：EatWhat 的架构文档写"不把服务端的 msg 和错误码直接给用户看"，Codex 那边改前端时的要求是"非 2xx 也要解析响应体，保留后端 message 加 HTTP status 加业务 code"，两者合起来是：信息要带到前端，但展示给用户的是友好文案。

例外：封禁原因、操作受限原因这类本来就写给用户的内容可以直接展示。

来源：2026-09-27 training-sys（Codex 转述）；2026-10-22 EatWhat 技术架构（文档辅助）。
