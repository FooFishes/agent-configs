# testing

一句话立场：测试克制，不为覆盖率堆测试；验收要在真实环境端到端看到效果，测真数据不测 Mock；测试失败修产品代码，不放宽断言。

## 条目

### 不要写过多测试，会定期筛掉莫名其妙的测试

为什么：四次原话："请你进行下一阶段的开发吧, 不要写过多测试"，"然后不要加测试"，"将现在所有的测试进行列举, 我需要筛选去除莫名其妙的测试"，"这个项目目前有多少测试"。不是反对测试，是反对 Agent 默认大量生成，并且亲自筛。

例外：暂无。

来源：2026-11-01 至 11-04 eat_what_app。

### 测试失败先判断是回归还是测试过时，修产品代码里的真实缺陷，不为了绿放宽断言

为什么："先读每个用例和被测代码, 判断是代码回归还是测试过时, 修根因, 不要为了通过而放宽断言"；"改的是产品代码里的真实缺陷, 不是放宽断言"。

例外：暂无。

来源：2026-10-16、10-17 AnkerHackathon（会话简报转述，与同期"不应该只加 limit"的亲笔纠正一致）。

### 测真数据，去掉 Mock

为什么："去掉 MOCK, 我们测真数据"。后端是正式环境无法造数据时，才专门搭一个 Mock 假数据的验收环境，并且明确那是验收用的，不是运行时的。

例外：后端不可控时搭独立的验收环境。

来源：2026-09-04 sentry-panel-frontend；2026-11-03 eat_what_app。

### 验收要在真实环境端到端跑通，包括穿过真实的反向代理

为什么："Open the production site, create a throwaway case, and confirm the change stream connects and delivers updates through the proxies"；"check in the browser that staff replies reach the user page in real time"；"跑一下 demo 吧 看看效果"。单测通过不算完，要在浏览器里看到效果。移动端"在 Android 的真机上"做全流程 UI Review，"虚拟机不装, 我们用真机"。

例外：暂无。

来源：2026-10-14、10-16 AnkerHackathon；2026-11-03、11-04 eat_what_app。

### 验证按完整功能点做，不按单个函数做

为什么："一个功能点结束后再进行验证，而不要一个小 func 的去验证"。

例外：暂无。

来源：2026-10-10 sentry-panel（Codex）。

### 接口改动后用脚本对契约做端到端验证，OpenAPI 作为交付文档而不是强制门禁

为什么："写一个 Python 脚本, 用于验证大部分接口在调用的时候有按照这次修改的返回进行响应."；"产出一份 openapi 文档, 供前端开发使用"；但"不写OpenAPI生成哦...不需要强制检查接口是否存在"。

例外：暂无。

来源：2026-09-04 SentryPanelBackend；2026-09-27 training-sys。

### 安全相关的测试要用真实的本地服务复现，正反两个用例都要有

为什么：SSRF 修复时用户自己写出了测试方案："补用例: 本地起一个 http 服务, 返回 302 指向 127.0.0.1 的另一个端口, 断言被拒绝; 正常的公网重定向 ... 能跟到底"。

例外：暂无。

来源：2026-10-13 Nova。

### 审查按影响面从大到小分类，先保证业务流程闭环没有漏洞

为什么："深度 Review 一下这个项目, 找出项目的问题. 按照由大到小的类别进行."；"先保证功能上业务流程能跑通闭环, 没有漏洞"。审查还要穷尽权限和错误边界："评价谁能干什么 谁不能干什么, 会产生什么报错. 尽可能穷尽一下."

例外：暂无。

来源：2026-09-26 至 09-28 training-sys。

### 构建通过不等于类型正确，不关闭构建期的类型和 lint 检查

为什么：发现 Next 配置里开着 ignoreBuildErrors 后，用户授权修掉一百多个类型错误并恢复检查。Codex 记忆里的结论是"不要将 pnpm build 作为前端类型正确性的证明"。

例外：暂无。

来源：2026-09-26 training-sys（Codex 转述）。

### 内部后台工具可以不测响应式布局

为什么："可以不测试响应式布局了"，一个月后再次生效。

例外：面向用户的产品要照顾宽屏，见 ui。

来源：2026-09-10、10-10 sentry-panel（Codex）。
