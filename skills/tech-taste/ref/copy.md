# copy

一句话立场：界面不放解释性文案，引导可以亲切，提示和报错用规范短句；用正式全称，不露技术缩写，不过度负反馈。

## 条目

### 界面上不放解释性、说明性文案，冗余的删掉

为什么：四个项目里反复出现："去掉这些莫名其妙的说明文案"，"你现在在上面使用了很多说明性文本, 这是不需要的, 你要搞明白产品定位"，"有些文案实际上是冗余的"，"换一下吧 更精炼一些"。空状态只写一句话，不复述卡片标题的含义："当前没有已发布且尚未提交的作业 与 已发布但尚未提交的作业 为无用的文案"。

例外：暂无。

来源：2026-09-04、09-07 sentry-panel-frontend；2026-09-23 webhook-relay；2026-09-26、09-28、10-07 training-sys。

### 内部技术工具不堆解释，维护者都知道的东西不写在界面上，说明放到 note

为什么："这个平台也不是面向普通用户的, 是技术人员维护用, 像这些我们都知道是怎么实现的, 字段是什么含义, 很多文案其实是不太有效的. 我们按照最终的产品形态做, 对于说明文案放到 note 中"；"像这种 '哪个接口, 因为什么在失败' 是不需要的"。

例外：暂无。

来源：2026-09-03 isdu-app。

### 引导可以亲切，提示和报错用规范短句；既不儿戏也不过于严肃

为什么：三次调整尺度："目前的文案有些过于口语了, 这是 UI 文案, 不应当这么儿戏"；"引导可以亲切，提示和报错用规范短句"；"文案我指的是不要过于严肃, 但是现在很多文案过于口语了吧"。

例外：暂无。

来源：2026-10-24、10-30 eat_what_app。

### 用正式全称，不暴露技术术语和缩写

为什么："去掉 (OIDC) 文案, 山大 改为山东大学"；"跳转到 i.sdu.edu.cn 授权，无需在本系统输入密码 去除该文案"。

例外：暂无。

来源：2026-09-26 training-sys。

### 警告和负面反馈只在真正失败时出现，不要宽泛地给负反馈

为什么："为什么搜索时无论搜索什么都会带上 来源不足 缺乏证据 一类"；"这个太宽了, 只有很少的情况才会这样, 或者用户问的实在搜不到才应该这样, 并且目前这个一整个框的总结找不到什么有点过于负反馈了"。

例外：暂无。

来源：2026-10-21 Nova。

### 校验提示在用户真正触发动作时才显示，不预先显示；能省步骤就省

为什么："底部, 应当在用户直接点击登录的时候, 才去显示请先勾选协议的文案."，后来进一步改成"弹出框, 用户同意后直接进行下一步"。

例外：暂无。

来源：2026-10-29、11-05 eat_what_app。

### 对外讲技术亮点从产品形态和用户感知出发，不代码化
