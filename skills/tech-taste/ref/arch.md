# arch

一句话立场：形态由职责决定，差异用通用抽象和数据表达而不是特判。外部服务隔一层不绑定供应商，遇到边界问题选正确的隔离而不是放宽。

## 条目

### 业务差异用通用抽象和数据表达，不在代码里按型号或场景写特判

为什么：特判每多一个型号就多一处代码，而且无法从信息库或配置生成；通用抽象加数据则只需要补数据。曾三次主动盘问"有没有针对某些型号做特判"，然后拍板做通用抽象。会变的展示映射同样做成配置数据，理由是"防止硬编码导致的无法维护"。

例外：暂无。

来源：AnkerHackathon、sentry-panel，2026-09 至 10。

### 外部服务必须有抽象层，不绑定供应商；暂不实现的能力也先抽接口，用本地实现顶上

为什么：供应商会换，一个赛期内就换过模型。有抽象层，替换是一次配置；没有，替换是一次重构。"不绑定供应商"是对外宣讲时主动列出的亮点。搜索、模型、推送都这样处理。

例外：暂无。

来源：Nova、AIC、AnkerHackathon、eat_what_app，2026-10。

### 服务端形态由它承载的职责决定，不默认做轻量方案

为什么：要承载账号、鉴权、统计、同步，就该是一个重的服务端，先做轻量 Worker 之后一定要重写。Agent 倾向轻量时被直接否决。

例外：暂无。

来源：Nova，2026-10。

### 职责相近的东西合并，不多加一层

为什么：每多一层都要有存在的理由。权限模型里 Teacher 和 Owner 差不多就让 Owner 管，筛选直接用上游原始值而不造一层中间的逻辑 key。

例外：暂无。

来源：training-sys、sentry-panel，2026-09。

### 遇到跨域、鉴权、CSP 这类边界问题，选正确的隔离边界，不放宽安全设置打补丁

为什么：放宽是拿安全换省事。为了预览功能愿意单独配域名、通配证书和一次性票据，就是不愿加 allow-same-origin。

例外：暂无。

来源：training-sys，2026-10。

### 多平台共用一份业务代码，差异收敛到固定位置，不维护平台分支

为什么：一处修复两边生效。平台分支迟早分叉成两个产品。

例外：暂无。

来源：isdu-app，2026-10。

### 实时更新用推送不用轮询，推送和可恢复要一起想

为什么：轮询是偷懒，推送只做一半又会漏消息。确认是轮询后立刻改 SSE，紧接着问的就是用户中途退出再进入还能不能收到后续消息。

例外：暂无。

来源：AnkerHackathon，2026-10。

### 延迟是一等约束，性能预算是硬上限不是目标值

为什么：多一跳代理"延迟必定上升"是否决走 CDN 的理由；Agent 把"十分钟可接受"当目标被纠正"大部分时候可以做到效率高一些"。开发环境卡顿和掉帧也算要查的性能问题。

例外：暂无。

来源：Nova、webrtc-turn、eat_what_app，2026-10 至 11。

### 分层要落到谁能 import 谁，对全局中间件和拦截器的副作用保持警惕

为什么：分层不是画图，要有导入导出规则才算存在。引入全局性机制前先问它"会影响实际的业务行为吗"。

例外：暂无。

来源：Nova、eat_what_app，2026-10 至 11。
