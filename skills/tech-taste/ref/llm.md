# llm

一句话立场：判断类任务交给模型而不是规则，但选型靠自己跑基准，替换前先做评测集。确定性的事情由代码做，守卫做减法而不是整条拒绝。

## 条目

### 判断和分类逻辑优先用模型，不写规则匹配，也不维护模型能替代的独立管线

为什么：规则穷举不完，模型能泛化。会主动盘点"哪里是靠规则匹配去做判断的"然后逐个替换。有多模态模型就不再维护独立的 OCR。

例外：暂无。

来源：Nova、AnkerHackathon，2026-10。

### 模型选型靠自己跑基准，替换核心组件前先做带标注的评测集，通过了再逐个替换并保留降级

为什么：模型之间的差异只有在自己的数据上才看得出来。要求约一百条标注问句的评测脚本，看延迟、准确率和置信度分布，还专门要求"删除泄题的结果重跑"。

例外：暂无。

来源：Nova、AnkerHackathon，2026-10。

### 延迟是选模型的一等约束，按任务类型分别判断

为什么：分类任务和强上下文生成任务的延迟容忍度不同。延迟敏感路径关掉思考或用最低档。两级分工时，轻量模型就是关掉思考的同系模型。

例外：暂无。

来源：AnkerHackathon、Nova，2026-10。

### 确定性的事情由代码做，模型只消费结果，模型推断旁边要有手动兜底入口

为什么：用户要改信息就直接改，把改完的状态交给模型，而不是让模型去改。AI 推断的结果旁边放一个下拉框之类的手动途径。

例外：暂无。

来源：AnkerHackathon，2026-10。

### 输出守卫只盯少数高风险类别，命中时删违规句保留其余，不整条拒答，不把 Agent 管死

为什么：过度守卫让 Agent "不够灵活智能"。允许回答通用问题，允许带一个追问，审查只查几类硬风险。

例外：具体盯哪几类是项目决定的。

来源：AnkerHackathon，2026-10。

### 向用户提问以信息增益为准，系统里已有的结构化数据不再问

为什么：目标是"让用户进行更少的操作，让 agent 获得更有价值的信息"。有了订单系统就直接读订单，不再问用户型号。

例外：暂无。

来源：AnkerHackathon，2026-10。
