# git

一句话立场：小步独立提交，一个提交只做一件事；提交信息是英文 type(scope) 加中文标题，不带 AI 署名；单人项目直接在主分支上做。

## 条目

### 每个独立的小改动单独提交，不写大提交

为什么：这是所有历史对话里重复最多的一条。training-sys 里连说了几次："对于每个小的更改, 都单独进行提交, 不要进行大的提交"，"每一小步更改都要进行提交啊, 不要写大提交"，"提交一下，分几个 commit. 每个小改动写成一个 commit 吧"，"在升级过程中进行小步的 push"。Anker 里是"按 3.1、3.2、3.3 分成三个提交"，"按照具体功能范围提交"，"把转人工后不再出排查卡片的修正也单独提交"。一次会话里 Agent 拆出了四十个提交，用户接受了。

例外：暂无。

来源：2026-09-26 至 09-28 training-sys（Codex）；2026-10-14 至 10-17 AnkerHackathon。

### 只提交本次改动，同一文件里不相关的部分按 hunk 挑出去

为什么：多个会话并行改同一个工作区时反复强调。"只提交叠放相关的改动, evidence-canvas.tsx 里只挑叠放的部分"，"提交助手这两轮的改动，同一文件里别处的改动不要带进去"，"只提交本次改动的文件，不要带上工作区里原有的画布改动"，"只把这次 Agent 放宽限制的改动挑出来提交, 不带另一个会话的订单商品与事实修改改动"。Codex 那边也是精确路径暂存，从不 `git add -A`。默认不接受"顺手带上"。

例外：暂无。

来源：2026-10-21 Nova（同一天六次）；2026-10-17 AnkerHackathon；2026-10-10 eat_what_app（Codex）。

### 提交信息用英文 Conventional Commits 前缀加中文标题，scope 用功能模块名

为什么：两次连续纠正定下来的格式。Agent 先用了英文标题，用户："不是, 你为什么要使用英文提交信息.."。Agent 改成全中文，用户又说："怎么前面那一部分也给我换成中文了"。另一次用了 `style(front)`，用户："参考之前的提交信息格式"，最后 amend 成 `style(dashboard): 将卡片操作按钮改为实心样式`。Nova 里的例子是 `fix(fetch): 跟随重定向时逐跳检查内网地址`。这个格式在 Spring Boot、Next.js、Flutter、Node 项目里都一样。

例外：暂无。

来源：2026-09-27、09-28 training-sys（Codex）；2026-10-12 至 10-22 Nova；2026-10-14 AnkerHackathon。

### 提交信息通常只写标题，不写 body；内容太多先拆提交，拆不开才用 body

为什么："这里对于不要加 desc"，"提交信息用中文 Conventional Commits……只写标题"，"提交这次移植的改动, 提交信息只写标题"。粘贴了一段带长 body 的提交信息后说"去掉这些"。唯一一次允许 body 是"提交吧, 记得拆一下, 或者把其他提交写在 desc"，优先级仍是先拆。

例外：拆不开的多项内容可以写进 body。

来源：2026-10-12 至 10-22 Nova；2026-10-08 training-sys。

### 提交里不带 Co-Authored-By 或任何 AI 署名尾注

为什么：四个项目里说了至少五次："Co Author 去掉"，"去掉 CoAuthor"，"帮我 amend 去掉 Coauthor, 然后force push"，"去掉 Claude 相关功能, 只保留 Generated by <model>"。如果一定要标注 AI 参与，只接受一行 "Generated by <model>"。

例外：暂无。

来源：2026-10-11 至 10-18 AIC、Nova、seekbench；2026-10-14 AnkerHackathon。

### 单人项目直接在主分支开发，已有分支用 fast-forward 或 rebase 并回去然后删掉

为什么：至少七次原话，跨四个项目。"直接提交, 不要开新分支"，"直接rebase过去, 之后所有更改直接在主分支上开发就好"，"ff 过去然后删除, 进行提交"，"直接 ff 吧"，"将 main 作为主分支吧"，"OK 在 main 上提交吧"。用户自己敲的也是 `git merge --ff-only`。偶尔走 PR 只是过个流程，不会等 review。

例外：实验性的大改动可以开 experiment 或 tmp 分支，事后按模块逐项择优并回 main，而不是整条分支二选一。"看一下 experiment/* 分支, 有值得并入主分支的内容吗"，"按 main 的规则追问，保留 tmp 的研究预算设计"。

来源：2026-09-07 sentry-panel 两端；2026-09-26 至 09-28 training-sys；2026-10-12 至 10-22 Nova。

### 临时文件、录屏、评测结果、构建产物不进仓库，发现误提交立刻删掉并补 .gitignore

为什么："删掉 apps/web/.tanstack/tmp 下误提交的临时文件，把 apps/web/.tanstack 加进 .gitignore"，"archive/vids 不进仓库, 把它加到 .gitignore"，"评测结果文件（results 目录）不提交"。

例外：暂无。

来源：2026-10-16、10-17 AnkerHackathon；2026-10-21 Nova。

### push 是有意的发布动作，推之前要知道会带上什么、会触发什么

为什么：main 自动部署的项目里，用户会明确控制推送时机："Don't push yet. Wait until the service.ts type fix is committed, then I'll push."，"先不提交, 我看完成片再说"。另一个会话提醒"这次推送会带上另一个会话的 d8d45f0，并触发线上部署"。

例外：暂无。

来源：2026-10-17 AnkerHackathon。

### 开源协议：产品仓库用 AGPL，工具和基准仓库用 Apache-2.0

为什么："会开源，用 AGPL 吧"（Nova 产品）；seekbench 工具仓库选了 Apache-2.0。

例外：这是两次拍板，样本少，换项目时问一下。

来源：2026-10-12 Nova；2026-10-18 seekbench。

### 仅本地使用的文件和配置绝不提交，AI 工具生成的目录也不入库

为什么："这是仅本地使用的啊,,, 为什么要提交"，"Android 把 Debug 也使用 release 签名吧, 仅本地不提交"，"ci/setup_jenkins.py 不提交"，发现 .grok、.lingma、.qoder、.zcode 四个目录后要求"删除这些内容... 不要同步到 Git"。

例外：暂无。

来源：2026-10-21 至 11-04 isdu-app、eat_what_app。

### 提交信息里不提开发阶段编号和文档序号

为什么："不在 msg 中提到阶段和文档中的序号"。对外讲功能时同样"不要提到开发计划中的 M 阶段, 只说功能"。阶段号是内部进度标记，不属于代码历史。

例外：暂无。

来源：2026-10-19 isdu-app；2026-10-25 Nova。

### 会回头审提交历史，找无意义的提交和顺手带上的多余改动

为什么："这些提交哪个是无意义的?"，"除了适配之外还有修改吗"，"Review 一下除了50314642之外的提交有什么问题"。

例外：暂无。

来源：2026-10-19 isdu-app。

### 有持续交付的 App 项目用 develop 出 Nightly、tag 出 Release，小改动直接在 develop 上做

为什么："develop 分支：直接打出来的包是 Nightly 包... tag：tag 对应我们的 Release... 手动打标：对于 PROD 的 Release"，"不用新建分支了, 直接在 develop 修改吧"。大重写另开 refactor 或 legacy 分支。

例外：这是 isdu-app 的分支模型，单人 Web 项目直接用 main，见上一条。

来源：2026-09-23、10-08 isdu-app。
